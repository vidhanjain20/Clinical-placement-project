# Technical Design Spec
## Clinical Learning Navigator — MVP v0.1

---

## 1. Data model

Six objects. Nothing more for MVP.

**Student**
- id, email, password_hash, name
- year_of_study, medical_school
- created_at

**Placement**
- id, student_id, name (e.g. "Cardiology"), start_date, end_date
- status (active / completed)

**Note** (a placement experience capture)
- id, student_id, placement_id, date
- raw_text — what the student typed or spoke, verbatim
- structured (json) — extraction output: conditions, skills, investigations, participation, confidence, learning_points
- gaps (json array) — gaps identified from this note
- next_actions (json array) — recommendations generated
- extraction_status (ok / failed / pending)
- created_at

**LearnerModel** (the longitudinal profile)
- id, student_id
- exposure (json) — conditions/presentations/investigations seen, with frequency and participation level
- skills (json) — skills performed vs observed, with recency
- gap_tally (json) — accumulated gap tags with frequency across all notes
- last_updated

**ActionLog** (follow-through tracking)
- id, student_id, note_id, action_text
- outcome (sought / observed / performed / practised / completed / skipped)
- logged_at

**PlacementMap** (curriculum reference for a placement, generated at setup)
- id, placement_id
- conditions (json array)
- skills (json array)
- competencies (json array)
- generated by AI at placement creation, editable by student

Gap tallies are stored on LearnerModel (updated incrementally on each Note save) — not computed on every read. This keeps the recommendation call cheap.

`gap_tally` keys are **canonical tags** (e.g. `ecg_interpretation`), not the raw phrasing a student used. Reconciling "ECG interpretation" and "reading ECGs" into the same tag is handled by the AI itself as part of Call 2 (see §2) rather than a fixed tag list — this keeps the extraction prompt fully freeform, at the cost of occasional merge mistakes the founder should spot-check during Phase 0/4.

`LearnerModel` is one running profile per student, not per placement. Starting a new placement does not reset exposure/gap history — a gap flagged in cardiology still counts once the student moves to surgery. Only `PlacementMap` (the curriculum reference) is placement-specific.

## 2. The core loop

Two AI calls per note submission. That's the whole intelligence layer.

```
1.  Student submits raw_text (typed or voice-transcribed).

2.  CALL 1 — Extraction prompt:
    Input:  raw_text + placement context (name, week number)
    Output: {
      conditions: [...],
      skills: [...],
      investigations: [...],
      participation: { observed: [...], performed: [...] },
      confidence: { low: [...], high: [...] },
      learning_points: [...],
      gaps: [...]   ← self-identified weaknesses from the narrative
    }

3.  Pull LearnerModel.gap_tally (last ~10 notes' gap history).

4.  CALL 2 — Recommendation prompt:
    Input:  today's gaps (raw phrasing) + gap_tally (canonical tags + counts)
            + placement_map + upcoming assessment date (if set)
    Output: [
      { action: "Practise", topic: "ECG interpretation", why: "...", how: "..." },
      { action: "Seek",     topic: "Syncope",            why: "...", how: "..." }
    ],
    gap_mappings: [
      { raw: "reading ECGs", canonical: "ecg_interpretation" },     // matched existing tag
      { raw: "syncope work-up", canonical: "syncope_workup" }       // new tag, none matched
    ]
    Max 3 actions.

5.  Save Note with extraction_status: ok.
6.  Update LearnerModel.gap_tally using gap_mappings from step 4 (increment existing
    canonical tags, add new ones) — this is what makes "you've flagged ECG
    interpretation three times" reliable even when the student's wording varies.
7.  Update LearnerModel.exposure incrementally.
8.  Return structured data + next_actions to client.
```

Call 2 is the differentiator: it sees the student's accumulated gap history, not just today, and it reconciles today's phrasing against that history so the count is accurate. "You've flagged ECG interpretation three times" can only come from this call having memory *and* correctly recognising that "reading ECGs" is the same gap as before — this is folded into Call 2's output rather than a separate third API call, since Call 2 already has both pieces of data (today's gaps and the existing tally) available to it.

Both calls are freeform — no fixed curriculum reference in MVP. The PlacementMap (AI-generated at placement setup) provides soft curriculum grounding without requiring us to source or maintain official UKMLA data.

## 3. Screens

Mobile-first. Four screens, no more for MVP.

**Screen 1 — Onboarding (one-time)**  
Year, medical school, current placement. One field per step, not a form. Takes 90 seconds.

**Screen 2 — Placement setup**  
Name the placement + duration → system generates PlacementMap (conditions/skills/competencies relevant to that placement). Student can edit the list. This takes 2 minutes and runs once per placement.

**Screen 3 — Capture + result (daily-use screen)**  
- "What did you see today?" — large text area, mic button for voice (Web Speech API, typing fallback)
- After submit: extracted tags (conditions, skills, gaps) shown as chips
- Recommendations panel: 1–3 actions with what/why/how
- "Did you act on this?" follow-through prompt for previous day's recommendations (shown at top if unanswered)

**Screen 4 — Dashboard**  
- Placement progress: conditions encountered X/Y, skills performed X/Y
- Strong areas (green), developing areas (amber), priority gaps (red)
- History: past notes as collapsed cards, tap to expand
- Recurring gaps panel: top 5 gap tags by frequency

No separate note-detail page — expanded card handles it. No analytics beyond what's on the dashboard. No settings screen in MVP.

---

## 4. Voice input

Browser-native `SpeechRecognition` (Web Speech API). Runs client-side, zero backend cost, zero latency added.

- Mic button appears alongside the text area
- Tapping mic starts listening; speaking fills the text area in real time
- Student can edit the transcription before submitting
- If `SpeechRecognition` is unavailable (Safari, Firefox, any non-Chrome mobile browser) — mic button is hidden, text area is the only input. No degraded experience, just no mic.

No server-side transcription (Whisper etc.) in MVP. The voice-to-text quality of Chrome's native API is sufficient for the capture use case, and it costs nothing.

## 5. Error handling

- **LLM call fails or times out** → Note saved immediately with raw_text and extraction_status: failed. UI shows "Saved — we'll process this when the connection recovers." Retry button. Raw text is never lost.
- **Malformed JSON from extraction call** → Retry once with a stricter output-format instruction. If still malformed, fall back to failed state.
- **Recommendation call fails** → Show extraction results without recommendations. "Recommendations unavailable — try refreshing." Note is still saved with gaps.
- **Empty or very short note** (< 20 chars) → Submit button stays disabled. Prompt: "Add a little more detail — even a sentence is enough."
- **Voice transcription produces empty string** → Mic button resets, text area remains focused. No error shown.

## 6. Tech stack

Reusing Continuity's proven stack to move fast:

| Layer | Choice | Reason |
|---|---|---|
| Frontend | React + Vite | Already proven in this repo |
| Backend | Node / Express | Same |
| Database | SQLite → Postgres | SQLite for solo pilot; migrate when load demands it |
| AI | Anthropic API (Claude) | Two calls per note submission |
| Auth | Email + password, session cookies | Individual accounts (not single-clinic like Continuity) |
| Hosting | Render / Railway / Fly.io | UK/EU region, cheap tier fine at pilot scale |
| Voice | Web Speech API | Client-side, zero cost |

No new dependencies added for MVP beyond the Anthropic SDK.

## 7. Privacy and compliance

- Students must not enter patient-identifiable information. This is stated at onboarding, on the capture screen, and in a basic privacy notice. Not technically blocked (impractical), but the product's responsibility is to make the expectation explicit.
- **Client-side PII nudge (non-blocking):** before submit, a lightweight regex check flags likely identifiers (full names in a "Mr/Mrs/Ms X" pattern, NHS-number-shaped digit sequences, dates of birth) and shows "this might include identifying detail — remove it?" The student can dismiss and submit anyway. Cheap to build, meaningfully reduces real risk, never blocks a submission.
- UK GDPR applies from first user. Hosting on UK/EU data-residency provider from day one.
- This product is educational software, not a medical device under MHRA rules — no diagnosis, treatment, or clinical decision support for real patients. Re-evaluate if scope expands.
- No data processing agreement required for MVP (individual students, not institutions). Have one ready for any institutional pilot.

---

## 8. Testing

- Unit tests: gap-tally aggregation, JSON parsing/fallback, PlacementMap generation logic. Deterministic, no LLM required. Same pattern as Continuity's `flagging.test.js`.
- LLM output quality: not unit-testable. Validate manually against 10–15 real example notes (your own placement experiences) before releasing to anyone else. The extraction and recommendation prompts need iteration against real input — this is founder work, not engineering work.
- Auth and note-save flows: manual end-to-end test before any external users.

---

## 9. Out of scope for MVP

- OSCE / virtual patient
- Official curriculum mapping (UKMLA, GMC outcomes)
- Supervisor or institution accounts
- Cohort or aggregated analytics
- Qbank or content library integration
- Spaced repetition scheduling
- Notifications / push alerts
- Native mobile app
- Automated competency sign-off
